# 日记编辑器设计与扩展约定

本文说明日记正文的数据模型、可视化编辑流程、图片版式语义以及新增区块时需要同步修改的位置。日记可以独立存在，旅行是可选的增强归属。

## 设计目标

- 普通使用者不需要学习 Markdown，选择内容类型并填写表单即可完成日记。
- 会 Markdown 的使用者也不需要维护隐藏语法；正文始终是可预测、可校验的结构化数据。
- 编辑器、模板、公开页面和备份使用同一份正文，不维护兼容层或第二套事实源。
- 前端仍随 Spring Boot Jar 发布，不拆分独立前端工程，不增加 npm 构建步骤。

## 唯一正文协议

正文存储在 `journal_entry.content_json`：

~~~json
{
  "schemaVersion": 1,
  "blocks": [
    {
      "id": "block_m2abc123",
      "type": "paragraph",
      "version": 1,
      "title": "",
      "data": { "text": "从成都出发。" },
      "settings": { "style": "normal", "align": "left" }
    }
  ]
}
~~~

字段约定：

- `schemaVersion`：整篇文档协议版本，当前为 `1`。
- `id`：区块内唯一且稳定的标识。
- `type`：受白名单控制的区块类型。
- `version`：单个区块的数据版本，当前为 `1`。
- `title`：可选区块标题。
- `data`：业务内容；不同类型拥有不同字段。
- `settings`：受控外观设置，不接受任意 CSS、HTML 或 JavaScript。

数据库迁移 `V11__journal_block_document.sql` 会删除旧的 Markdown、模板填写数据、模板快照和脱离状态字段。该迁移面向尚未正式上线的开发阶段数据，不提供旧正文兼容转换。

## 内容块目录

当前提供 29 种内容块：

- 文字：正文、小标题、引用、提示卡片、信息清单、优缺点、表格、链接卡片。
- 记录：清单、评分、数字亮点、同行的人。
- 旅行：旅行信息、今日开场、路线、行程、时间线、花费、地点卡片、美食、住宿、交通、天气、今日小结。
- 图片：单张图片、图片组、旅行明信片。
- 排版：章节节点、分隔线。

### 一天的开头、中间和结尾

`day-opener`、`chapter`、`day-summary` 是三个为「一天」服务的区块：

~~~text
东京 · Day 4              ← day-opener
8月10日 · 晴
浅草 → 上野 → 银座
21,430 步   ¥ 8,420

08:30 · 清晨              ← chapter
正文
照片

18:40 · 银座              ← chapter
正文

今天最喜欢 🌟 浅草的清晨   ← day-summary
今日花费   💴 ¥ 8,420
~~~

它们要的东西——城市、第几天、当天路线、当天花费——**全都已经在旅行工作台里了**，让作者再抄一遍没有意义。所以 `day-opener` 和 `day-summary` 加进了 `LINKABLE_BLOCKS` 且**默认就开着数据关联**：打开配置弹窗时已经填好，作者只需要补一个天气、写一句「今天最喜欢」。

独立日记没有旅行上下文时不展示旅行数据关联，现有正文快照保持不变；以后归入旅行后再显示城市、行程、预算等关联能力。

天气和「今天最喜欢」不自动填，因为它们没有数据源——那是作者对这一天的判断，不是能推出来的事实。

`chapter` 是排版类，不关联数据。它本质上是带时间锚点的小标题，作用是让长日记读起来有节奏。

## 写作在前，能力在后

29 种区块是能力，不该成为写作入口。编辑器按「要不要填表」把区块分成两类：

| 分类 | 区块 | 编辑方式 |
| --- | --- | --- |
| 连续写作 | `paragraph`、`heading`、`quote`、`callout` | 正文里直接编辑，不弹窗 |
| 需要填表 | 其余 25 种 | 区块配置弹窗 |

分流规则写在 `journal-block-editor.js` 的 `INLINE_BLOCKS`。inline 区块用自增高的 `textarea` 呈现，字号、引用竖线、提示卡底色都对着 `journal-blocks.css` 的公开端样式做，编辑时看到的就是发布后的样子。选用 `textarea` 而不是 `contenteditable`，是因为后者在中文输入法组合输入时的光标恢复非常难做对。

连续写作的键盘行为：

- `Enter` 交还给原生 `textarea`，桌面键盘和手机软键盘都在当前组件内换行。
- 工具行的“＋正文”在当前组件下方新建一个 `paragraph`，需要拆开结构时才显式点击。
- 输入法组合中的 `Enter` 同样由浏览器原生处理，不会切断拼音选字。
- 段首 `Backspace` 与上一段合并，光标停在接缝处。
- `↑` `↓` 到达首尾行时跨到相邻段落。

换行直接存为文本里的 `\n`，公开端渲染成 `<br>`。“＋正文”由 `insertParagraph` 实现，在段落、小标题、引用和提示卡的工具行都可用；它只新增空正文组件，不偷偷改动当前文字或光标附近的内容。

打字不会每一键都上报文档：inline 输入攒 300 毫秒才 `commit()`，结构变化（新增正文组件、退格合并）立即提交。这段窗口内组件不接受父组件的回流，否则光标下的那段字会被旧快照顶掉。

添加内容分两层：`＋` 先给 8 个常用区块（`QUICK_BLOCKS`：图片、章节节点、地点卡片、小标题、今日开场、图片组、今日小结、分隔线），正文不在其中——直接写字或点“＋正文”即可；完整的 29 种收在「更多内容」后面，带搜索和分类。区块列表中的图片仅作限高缩略展示，避免一张图片占满整个写作区域；完整效果在图片设置弹窗和公开页面中查看。非 inline 组件双击主体即可打开设置，原有“编辑”按钮继续保留。

## 图片管理与插入

图片管理支持：

- 文件选择、拖放和剪贴板粘贴上传。
- 缩略图与放大预览。
- 单张或多选插入。
- 图注、设置封面、删除和批量删除。
- 按 EXIF 拍摄时间排序和拖拽手工排序。

从“添加内容”选择图片块，或从右侧图片管理点击插入，都会进入同一个图片设置弹窗，不存在两套图片配置逻辑。

### 图片设置分组

- 内容：选择图片；明信片在这里填写地点、日期、寄语和署名。
- 版式：宽度、位置、图片组排版、列数和显示比例。
- 外观：相框、圆角及电脑悬停效果。
- 图注：图注文字和显示位置。

**图注只在「图注」里填。** 内容页曾经也放着一个图注输入框，两个框绑同一个字段——看起来像两个设置，改哪个都行反而让人犹豫。

预览区渲染的是**整篇真实文章**，用的是和「预览全文」、公开页面同一套 `render`：正在编辑的那一块高亮，改设置实时跟着变。四档宽度都相对正文栏计算，前三档在两侧留白，只有“正文宽度”和文字左右对齐。

### 图片长什么样，只由这里决定

**一个「跟随主题」都没有了。** 宽度、相框、圆角、图片组排版这四项打开弹窗时空值就地补成具体值并选中（`fillMissingImageSettings`，默认 `medium` / `none` / `soft` / `grid`）。作者看到的就是这张图实际长什么样，不用在脑子里把「跟随主题」翻译成一个宽度。

主题外观那边对应的配置**整组删掉了**（见 `V30__drop_theme_image_tokens.sql`）：「图片默认版式」「多图布局」两组、形状里的图片圆角、互动里的鼠标经过照片。两套设置并存时，作者在主题里改一下看不出变化——逐张设过的优先——那种「到底谁说了算」的场合永远解释不清。现在只有一套。

跟着变成固定值的还有首页列表卡片的封面：它的比例、圆角、内边距、阴影本来和「图片默认版式」共用同一组 token，那组没了就退回 `public.css` 里写死的 16:9 和基础主题的 `--tj-image-radius`。这是删这组 token 的代价，卡片封面本来也不在图片编辑的管辖范围内。

改默认值只改 `JournalBlockEditor.vue` 里 `IMAGE_DEFAULTS` 和 `GALLERY_DEFAULT_LAYOUT`。

### 下线一种版式要改三处搬运表

通栏出血、瀑布流/杂志版/故事流/错落画廊、除胶带和胶片以外的相框、整个色调设置、图注的「覆盖底部」都已下线，CSS 一并删了。删选项只是第一步——库里、以及作者浏览器里存着旧值的正文都得搬到保留集合，否则它们会落进「设置面板一个选项都不高亮、渲染又什么都不套」的空档。三处搬运表一一对应，**必须同时改**：

| 位置 | 管的是 |
| --- | --- |
| `V29__retire_image_block_settings.sql` | 库里已经存着的日记正文和模板 |
| `JournalDocumentService.RETIRED_SETTING_VALUES` | 提交上来的旧值——静默搬运，不 400 |
| `frontend/src/journal/document.ts` 的 `RETIRED_SETTING_VALUES` | `normalize()` 这条路，主要是 IndexedDB 里的本机草稿快照 |

后两处不能省成「拒收」：本机草稿快照迁移够不着，一拒收自动保存就一路失败，而作者根本不知道是哪一块出了问题。

### 预览宽度必须和读者一致

读者那边是 `.article { width:min(var(--tj-article-width,760px),100%) }`，图片的每一档宽度都相对它计算——预览宽窄不对，同一张图在这里和发布之后就是两个大小，看了也白看。`box-sizing` 是 `border-box`，所以 `.article-preview-body` 的内边距和那 2 px 边框都得加回 `width` 里，内容盒才正好是正文宽。

这个约束是「图片配置弹窗」「预览全文」「窄屏的看效果」三处共用的，它们都套 `.article-preview-body`。

### 宽屏并排，窄屏一个按钮

窄屏（≤780 px，和弹窗转全屏同一个断点）地方不够并排，改成一个「👁 看它在文章中的效果」按钮，点开是整篇的全屏预览；宽屏保留并排。断点判断在组件里用 `matchMedia` 做，**不是 CSS 隐藏**——留在 DOM 里只是看不见的话，`keepFitted` 仍会在一个高度为 0 的容器上量来量去。

正在调的那一块按当前设置就地放回整篇里：编辑已有区块就替换原位，新增则插到它将要落脚的位置，所以预览里的前后文和确认之后一致，而不是把它挂在文末。

### 图片配置铺满整屏

它要同时装下 760 px 的正文预览和设置面板，1400 px 都紧张。整屏之后左边给足 760，右边设置面板也有完整的高度可滚。有两处容易踩：

- 遮罩层 `.el-overlay-dialog` 给弹窗留着 16 px 内边距，全屏时必须归零，否则四周露一圈就不是整屏。
- `.block-config-dialog--full .block-config-form` 和 `.block-config-dialog .block-config-form` 特异性一模一样，**谁写在后面谁生效**。全屏那组覆盖必须排在通用规则之后。

确认/取消放在设置栏底部，而且必须在滚动区**外面**（grid 的第二行）：搁在里面的话，内容短的那个 Tab 滚不起来，`sticky` 不生效，按钮就跟在内容后面浮着，切一次 Tab 换一个位置。

全屏这个类跟着「图片块**且**宽屏」走，不能只看是不是图片块——窄屏本来就有自己那套全屏样式，跟着加上的话，全屏规则会把弹窗自带的 footer 藏掉，而侧边按钮又只在并排布局里渲染，手机上就一个按钮都不剩。

### 改一个设置就重新定位

改设置的人正盯着这一块看它变成什么样，可换个宽度、换个比例之后它上下的高度全变了，长日记里翻两下就找不着。所以每次重算预览都把它带回视野中间，哪怕刚刚手动滚开过。

图片加载完还会再对一次位：刚插进来的 `<img>` 占的是按宽高比留出的位置，和最终高度未必分毫不差，何况弹窗那时可能还在入场动画里。要是这期间已经换去编辑别的块，就不再拽回来。

### 设置面板只有一个滚动区

以前是三层嵌套：表单自己滚、四个 Tab 共用的内容区滚、图片选择器还有一层。手指往下一划，滚的是哪一层全看落点在哪。现在只有 `.block-config-form` 滚，里面一律按内容自然铺开。区块标题 `sticky` 钉在顶上——往下翻版式、外观、图注时都还想知道自己在配哪一块。

`.option-chips` 排成等宽网格而不是按文字长短流式排列：「手账胶带」和「直角」一长一短、下一行又错开另一个位置，十来个选项堆下来就是一片参差。

### 设置生效范围

界面只展示当前排版实际支持的设置：

- 左中右位置在“正文宽度”下没有意义，因此隐藏。
- 列数只适用于规则网格。
- 前后对比只渲染前两张图片。
- 电脑悬停效果不会在触摸设备上触发。
- 图注右置在手机端自动回到图片下方。

图片组模式包括规则网格、横向并排、主图拼贴、轮播、胶片条和前后对比。胶片条在手机上原生滑动，在电脑上支持鼠标拖动和滚轮横向浏览。轮播的左右按钮落在图片**外面**——两侧留白由 `--carousel-nav` 算出，容器窄的地方（预览纸）调小这个变量即可，窄屏本来就靠滑动翻页、不出按钮，留白也一并收掉。

### 三种版式在区块列表里是静态的

轮播、胶片条、前后对比的横排结构是 `JournalMedia.enhance` 在渲染后重排出来的，而**区块列表的缩略图不跑 `enhance`**：缩略图上就写着「点击编辑查看完整效果」，整张卡片点一下即进配置，再套一层轮播的箭头和圆点只会打架。代价是它们会退化成一张张竖着堆，所以 `journal-block-editor.css` 里给这三种版式补了静态横排样式，只在 `.block-editor-preview` 作用域内生效。

图片一律 `flex:1 1 0`（基准是 0，多少张都在同一行等分，不换行）。**不要让它换行**：一换行就成了「缩得越窄、行数越多、反而越高」，和等比缩放凑一起会来回打架。`flex-wrap` 只是为了让说明文字掉到第二行。

### 图片的加载时机

一律 `loading="lazy" decoding="async"`：正文、公开端、区块列表、配置弹窗的整篇预览都是。区块列表和整篇预览都是一长条几十张图的滚动列表，全部立即加载并同步解码在手机上就是白白卡一下。

`renderBlock` 上还留着一个 `eager` 选项，会输出 `loading="eager" decoding="sync"`。它是为「弹窗里只渲染单独一块」那个旧形态加的——那种场景下内容一变整块重画，值得抢在同一帧画完。现在预览渲染的是整篇，**这个选项没有调用方**。

## 上传占位协议

旅途中的常见需求是「刚拍的这张，放在我正写的这段后面」，走一遍图片管理器（上传 → 等待 → 回列表 → 选中 → 插入 → 配置）太长。所以选完照片先在正文占位，上传在后台跑：

- 单张插入 `image` 区块并带 `data.pendingKey`；多张合并成一个 `gallery` 区块，带 `data.pendingKeys` 数组。
- 占位期间显示本机缩略图和上传进度，失败可单独重试或移除。缩略图由 `media/local-preview.ts` 先缩到最长边 256px 再显示：手机拍的是 4000×3000，把它的 Object URL 直接塞进那个 56px 的占位框，浏览器仍要解码上千万像素，选三张就够让页面白一下、抖一下。上传的仍然是原始 File，服务端拿到的字节和作者选中的完全一致。
- 缩略最多两张并行，避免一次选十张时的内存峰值；上传完成后要等 Vue 换上服务端缩略图（`nextTick`）再撤销本机 URL，否则中间会闪过一帧空图。
- 上传成功后把真实 `mediaId` 填回去，`pendingKey` 随之删除。
- 并发 3 条上传，一张失败不阻塞其余。

### 顺序必须是挑选顺序

并发上传下完成顺序不等于挑选顺序：选了三张，第三张最小最先传完，直接 push 的话就成了「3、1、2」。两处都要处理：

- **图片管理器列表**——每张照片在挑选时分到一个单调递增的 `seq`，传完后插到第一个序号比它大的元素前面。一批传完再按本地顺序调一次 `reorderMedia`，因为服务端的 `sortOrder` 是按请求到达顺序写的。
- **正文里的图片组**——`gallery` 区块额外带 `data.pendingOrder`（挑选时的 key 顺序，不可变）和 `data.pendingResolved`（key → mediaId）。每传完一张就按 `pendingOrder` 重排一次 `mediaIds`，全部传完后三个临时字段一起删掉。

`pendingKey` / `pendingKeys` / `pendingOrder` / `pendingResolved` 都只是本地状态，不进数据库：`body()` 提交前会清洗一次，把已完成区块的临时字段抹掉，把还没传完的整块剔除——否则服务器上会留下没有图片的空图块，刷新之后既看不到进度也传不下去。

后端不需要认识这些字段：`JournalDocumentService.collectMediaIds` 对 `null` 直接跳过，带占位的文档本来就能存草稿。

### 照片本身也要能活过一次关机

`File` 只活在内存里，浏览器被系统杀掉就没了。所以选中照片后先把 Blob 落进 IndexedDB（`local-draft.js` 的 `photos` store）再开始传，进编辑器时按正文里残留的 `pendingKey` 对上号接着传：

~~~text
地铁断网 → 拍照 → 继续写 → 浏览器被杀 → 重新打开 → 照片还在 → 有网自动续传
~~~

直接存 Blob 不转 base64：一张 4MB 的照片转成 base64 是 5.5MB 的字符串，十几张就能把手机浏览器的内存吃光，而 IndexedDB 原生就支持 Blob。

传完、或者作者删掉那个占位块时，本机那份副本一并清掉。队列里已经没有对应占位块的（作者后来删了那一段）在下次进编辑器时顺手回收。`online` 事件会把失败的那几张重新排上——旅行中最常见的是「进地铁 → 传失败 → 出站有信号」，让作者自己回来点重试很不合理，他这时通常已经在看风景了。

## 移动端行为

编辑器在手机上只有**一条纵向滚动**：`.editor-page` 是唯一的滚动容器，顶栏 `sticky`、底部工具栏 `fixed`，内部的正文区、区块列表一律不再各自滚动。之前是「页面锁住不滚 → 正文自己滚 → 分段 Tab 再滚 → 弹窗又滚」，软键盘一起来就得到处打补丁。

- 顶部只留返回、保存状态和 `···`，下面一行自动显示「8月10日 · 东京」。
- 日记信息、图片管理、拍照选择都是从下方推上来的 Bottom Sheet，各自内部只有一个滚动区。
- 软键盘缩小 `visualViewport` 时，底部工具栏随键盘上移，正文补足同等滚动空间；隐藏镜像按 textarea 的真实光标行定位，长组件中间的光标也不会被遮住。
- 底部工具栏固定 `＋ 📷 📍 H ”` 和图片入口，新内容插在光标所在段落之后。
- `--visual-viewport-height` / `--browser-bottom-inset` 现在只服务于弹窗，正文不再依赖它们。
- 图片排序以「按拍摄时间 / 按上传顺序 / 自定义」下拉为主，HTML5 拖拽退为桌面端的补充手段。

### 屏闪先看表现，再找病因

四类闪表现不同、病因无关，别一上来就怀疑图片：

| 表现 | 病因 |
| --- | --- |
| 背景闪黑/灰，内容和布局不动 | 遮罩露出来了 |
| 尺寸先大后小跳一下 | 缩放参数和内容不同帧 |
| 图片空白一下再出现 | `<img>` 被重建、重新解码 |
| **整块（含纯 CSS 元素）一起白一下** | **合成层作废重新光栅化** |

第四类**只在真机复现**：桌面开仿真设备换的是视口尺寸和 UA，渲染仍走桌面 GPU 和桌面解码器，凡是牵涉合成、光栅化、解码开销的病因一律测不出来。分辨它靠一个问题：**预览里那几条纯 CSS 画的灰色文字线是不是也跟着白？** 跟着白就是整层没了，与图片无关；只有照片那块白才是解码问题。

- **全屏弹窗要关掉 `dialog-fade`。** 它是 `translate3d(0,-20px,0)` + `opacity` 0→1，而遮罩是 `rgba(0,0,0,.5)`：桌面端弹窗居中、四周本就露着遮罩，这动画很自然；铺满整屏后它就变成「先上移 20px 露出底部黑边、再半透明地让黑色透上来」。`.block-config-dialog`、`.block-catalog-dialog`、`.article-preview-dialog` 都在**各自全屏生效的断点里**关掉 `animation`，并把遮罩底色改成面板同色兜底。
- **预览缩放不许用 `transform`。** `transform` 会把预览交给合成器单独栅格化，缩放比一改整层缓存作废，手机 GPU 按新尺寸重画要一到几帧、期间那层是空的。`keepFitted` 量出比例写进 `--fit-scale`，由 CSS 接到**正文栏宽度**上：图片是 `max-width:100%` + `height:auto`，栏窄一圈图片就小一圈，高度按固有比例自己跟上，全程只是普通布局。同理不要给它加 `transition`——比例是量出来的布局结果，不是状态切换。
  - 那些不随栏宽走的固定尺寸（假文字线的高度、段落间距）也要乘上 `--fit-scale`，否则缩得越狠它们占比越大，算出来的高度对不上。
  - 栏宽一变高度就跟着变，所以**测量前必须先把 `--fit-scale` 归位**，否则拿缩过的高度再算一次会越缩越小。归位和写回在同一个任务里完成，中间只有布局没有绘制。
  - `zoom` 是死路：Blink 的 `zoom` 只缩绝对长度，不缩百分比，而正文栏是 `width:72%`。
- **预览内容就地更新，不要整棵重建。** `v-html` 每次都给 `innerHTML` 赋值，哪怕新旧只差一个 class，里面的 `<img>` 也会销毁重造、重走加载和解码。`admin/patch-preview.ts` 先比对新旧结构，形状一样就只改属性和文字（值相同的 `src`/`srcset` 一个字都不写，写回同一个字符串也会让浏览器重新取图），结构真变了才整棵替换。更新前先 `teardown`：轮播这类会往块里插结构，不还原就永远比不上形状。
- **缩放重算不能晚于内容更新。** `watch` 已经是 `flush:'post'`（DOM 更新后同步执行），**别再套 `nextTick`**——那会把重算推迟一个微任务；只在 `previewEl` 尚未挂载（弹窗首次打开）时才退回下一拍。观察者要连容器一起 `observe`，否则「容器变高了」只能等下一次内容变化顺带纠正；弹窗关闭时要撤掉观察，容器高度塌成 0 会被算成缩到底。

改这一块的样式时，对某个 CSS 属性的行为拿不准就实测，别凭印象——`frontend/node_modules` 里有 playwright，几十行脚本就能在 Chromium（和 Android Edge 同引擎）里量出真实盒子：

~~~js
import { chromium } from 'playwright'
const page = await (await (await chromium.launch()).newContext()).newPage()
await page.goto(pathToFileURL('/tmp/check.html').href)
console.log(await page.evaluate(() => document.querySelector('#x').getBoundingClientRect().width))
~~~

`zoom` 不缩百分比、`grid-auto-flow:column` 下 `grid-column:1/-1` 跨不满，这两条都是这么当场量出来的，凭记忆写的方案在提交前就被否掉了。

## 发布前预览

「预览全文」（顶栏的 👁 / 手机的日记信息面板）就地把整篇渲染成读者看到的样子，用的是公开端同一套 `JournalBlocks.render` 和 `.journal-document` 样式，渲染后还会挂上 `JournalMedia.enhance` 让轮播、胶片条和灯箱能点。桌面和手机都铺满整屏——读者是在整块屏幕上读这篇文章的。

**入口只有顶栏那一个 👁，两种状态共用。** 它曾经只写在草稿那一支的操作组里，已发布的日记那一支只有「查看文章 / 撤回 / 更新发布」，而「查看文章」打开的是线上已发布的版本，看不到手里还没保存的改动——等于已发布的日记在桌面上没有预览。加操作按钮时注意别再把它塞进某一个分支。

数据全在本地，不需要先保存，也不签 token。要把草稿发给别人看才用「预览链接」——那个会签发一个 48 小时有效的 token 并复制到剪贴板。

## 草稿与发布语义

草稿和发布是**两套校验标准**。写的时候不该被表单拦住，公开出去的文章才需要完整。

| | 草稿 | 发布 |
| --- | --- | --- |
| 标题 | 可以为空 | 必填 |
| 正文 | 可以为空 | 至少一个区块且有实际内容 |
| slug | 留空由服务端生成 | 必须合法 |
| 日期 | 留空默认今天 | 必填 |
| 图片归属 | 校验 | 校验 |

对应的接口：

- `POST /api/admin/journals/draft` — 开一篇空草稿，`tripId` 可省略。**不是进页面就调**：只有作者真的写了点什么才调（见下面「草稿什么时候才真的创建」）。
- `PATCH /api/admin/journals/{id}/draft` — 自动保存，字段可以缺席，缺的沿用库里的旧值。只对 DRAFT 开放。
- `DELETE /api/admin/journals/{id}/discard-empty` — 作者**显式**放弃一篇空草稿时才调。是否真的为空由服务端判断，标题、摘要、正文、图片有任何一样非空就原样保留。

保存节奏（`js/admin/journal-editor.js`）：

~~~text
输入 → 停手 600ms  → 写本机 IndexedDB
     → 停手 3s     → PATCH 提交服务器
     → 45s 兜底    → 一直不停手打字时也不会太久没落库
     → 切到后台     → flushInline + 正常排队保存
     → pagehide     → flushInline + fetch(keepalive)
~~~

三处细节都是踩过的坑：

- **离开前必须先 `flushInline()`。** 正文的击键攒在 300 毫秒的去抖里，不先压下来就既进不了本机快照也进不了服务端——「写完最后一句话直接锁屏」正好会踩中这个窗口。组件卸载时也要主动压一次，因为父组件的 `onBeforeUnmount` 比子组件先跑。
- **`pagehide` 走 `fetch(keepalive)`。** 那之后普通 XHR 会被浏览器直接掐掉。用 `fetch` 而不是 `sendBeacon`，是因为这条接口是 PATCH 且要带 CSRF 头，而 `sendBeacon` 只能发 POST 且改不了请求头。只是切到后台时页面还活着，走正常的排队保存就行，没必要绕过队列去和正在路上的那次抢时序。
- **写请求排一条串行队列。** 自动保存、手动保存、发布、更新发布都会把整篇正文全量写上去。一旦两个请求同时在路上，先发的那个晚一步到达就会用旧正文盖掉新正文——在信号不好的地铁或山里，这种时序错位并不罕见。前一个失败也要让后面的继续排，否则一次网络抖动会让这一篇彻底不再保存。
- **队列之外还要一层版本号。** 串行队列只管得住当前这个标签页，管不住第二个标签页和另一台设备。`journal_entry.revision` 是乐观锁：每次保存带上手里那份的版本，服务端用带条件的 UPDATE 原子加一，版本对不上就返回 409。冲突时**不覆盖任何一边**——先把本机快照落盘，再让作者选「加载服务器版本」还是「保留本机内容」。`pagehide` 那条 keepalive 请求同样带版本；如果此刻已经有一次保存在路上，它带的必然是旧版本，那就干脆不发，只保住本机快照。

  版本号在 HTTP 层是**必填**的，不是「带上更好」：草稿 PATCH、全量 PUT、发布和撤回，缺了 `expectedRevision` 一律 400。以前缺席表示「不做并发检查」，于是「忘了传」和「故意不传」长得一模一样，任何新写的客户端只要漏掉这个字段就静默退回 last-write-wins——而那正是乐观锁要挡的那种数据丢失。确实需要无条件覆盖时显式传 `force: true`，让这个决定留在请求里看得见。

正文快照存 IndexedDB（`js/common/local-draft.js`），localStorage 只留一个「最近编辑的是哪篇」的指针。localStorage 的读写是同步的，一篇长日记每敲一个键就 `JSON.stringify` 再同步落盘，在手机上会直接卡住输入。

### 草稿什么时候才真的创建

打开 `/journals/new` **不再**向服务端开草稿。以前是一进页面就开，于是点一次侧边栏「写日记」就多一条空记录，看一眼退出也留下一条。

现在延迟到第一次有效编辑：标题、正文、摘要、旅行、城市、日期、标签、主题、选照片、用模板、手动保存、生成预览链接、发布——这些才算数，初始化时填进去的默认日期不算。

首次输入、模板生成和图片上传常常在同一瞬间到达，所以 `ensureDraft()` 共享同一个创建 Promise，无论多少条路径同时触发都只开一篇。创建成功后只接收服务端才有资格决定的字段（id、slug、revision），**不能**用整个空白响应覆盖表单——那会把作者刚敲进去的字抹掉。

断网时开不出服务端草稿，这时用一个负数当本机临时 id：正文快照和待上传照片先落在 IndexedDB 的这个 id 下（负数不会和服务端主键撞车，`photos` 索引的 `Number(journalId)` 也照常工作）。联网后创建一次真正的草稿，再把这两样整体改挂到真实 id 上——照片的 key 不变，所以不会重传。

侧边栏「写日记」和编辑器共用 `/journals/:id` 这一条路由，Vue 会复用组件而不是重新 setup。组件里 watch 路由参数，切回 `new` 时显式把 id、表单、上传队列和定时器清一遍，否则会带着上一篇继续写。

### 空草稿为什么不在退出时删

延迟创建之后垃圾记录少了很多，但仍然会有：写了半句话就退出的那些。这件事**必须在服务端按时间做，不能在浏览器退出那一刻做**：退出瞬间最后一次自动保存可能还在路上，那时服务端看到的空正文并不代表作者什么都没写。删错一篇正文的代价远高于库里多留一天的空记录。

所以退出时不再调 `discard-empty`，改由 `EmptyDraftCleaner` 每小时扫一次，回收**最后更新超过 24 小时**且标题、摘要、正文、封面、图片全空的草稿。静默期里作者随时可能回来接着写。

已发布的日记仍然只把快照暂存在本机，不由自动保存改变公开内容；点击“更新发布”才提交，原始发布时间保持不变。点击“撤回”后状态回到草稿，公开页面立即不可见。

## 扩展一个新区块

新增区块时至少同步以下位置：

1. `journal-blocks.js`：目录信息、默认数据、统一渲染和示例数据。
2. `journal-block-editor.js`：结构化填写表单；如果新区块属于「连续写作」类，还要加进 `INLINE_BLOCKS` 并补上行内轻控件。
3. `journal-block-editor.css`：编辑态样式；`journal-blocks.css`：后台与公开端共用的展示样式。
4. `JournalDocumentService.java`：类型白名单、设置白名单、正文有效性和媒体引用提取。
5. 模板服务：如果新区块需要被日记模板生成，再增加模板输入与生成规则。
6. 自动化测试：覆盖合法文档、非法设置、发布时有效内容和媒体归属。

不要只在前端添加类型。后端校验与公开渲染缺失会造成保存失败或公开页面丢失内容。

在加新区块之前先想清楚：29 种已经能覆盖绝大多数旅行场景，多一种就多一份决策成本。真正影响体验的通常不是少了哪种排版，而是输入摩擦、离线可靠性和从拍照到记录的路径长度。

如果新区块要的数据旅行工作台里已经有（城市、行程、账目、图片），把它加进 `LINKABLE_BLOCKS` 并在 `bindingDefaults` / `applyBinding` 里补上映射，而不是让作者再录一遍。`day-opener` 和 `day-summary` 更进一步——它们默认就开着关联，因为那些字段作者手填毫无意义。
